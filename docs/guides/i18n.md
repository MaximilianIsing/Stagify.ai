# Internationalization (i18n)

The site is translated into **11 languages** — English (source), Spanish, Chinese,
Korean, French, German, Dutch, Italian, Portuguese, Russian, Japanese — and each
language is served at **its own URL** so search engines index every market. Prices are
**always shown in USD** regardless of language.

- **English** is the default, served at the site root (`/`, `/guides.html`, …).
- **Every other language** is served under a URL prefix: `/es`, `/fr/guides.html`,
  `/de/contact.html`, … **rendered server-side** from the same language JSON, so a
  crawler (or a no-JS client) sees fully-translated HTML with a distinct, canonical,
  crawlable URL per language.

> **Why the URL matters.** Previously the translation was 100% client-side on a single
> URL, so Google only ever indexed English — the translated content was invisible to
> search in the other 10 markets. Serving each language at its own URL (with `hreflang`)
> is what makes those markets findable. This is a **serving/routing** layer on top of
> the existing translation JSON — not a second copy of the content.

## The pieces

### Config — the single source of truth

[`lib/i18n/locales.js`](../../lib/i18n/locales.js) defines **which languages get a URL
prefix** (`LOCALES`) and **which pages are localized** (`LOCALIZED_PAGES`), plus the
helpers (`localizedUrl`, `buildHreflangCluster`, …) everything else derives from. Change
the language or page set **here** and the router, sitemap, and hreflang all follow.

The localized page set is the indexable marketing/legal pages: `/`, `ai-designer.html`,
`masking-studio.html`, `stagify-plus.html`, `enterprise.html`, `guides.html`,
`contact.html`, `/status`, `privacy.html`, `terms.html`. Deliberately **excluded**: the
blog (articles aren't in the translation JSON — English-only), `faq.html` (canonicalizes
to `/index.html#faq`), and the auth/app pages (noindex).

### Server — request-time rendering

[`routes/i18n.js`](../../routes/i18n.js) registers `/<prefix>` and `/<prefix>/<page>` for
every locale × page and renders them through
[`lib/i18n/render-page.js`](../../lib/i18n/render-page.js), which:

- applies the same `data-lang*` attributes + `<title>` / JSON-LD the client uses, so the
  body ships already-translated;
- sets `<html lang>` + a `data-locale` marker the client reads;
- injects **`<base href="/">`** so every relative asset URL (including ones scripts build
  at runtime — logo images, the heic2any worker, the `languages/<lang>.json` fetch)
  resolves against the site root, not `/<prefix>/`;
- writes a self-referential `<link rel="canonical">`, the full `hreflang` cluster, and
  localized `og:*` / `twitter:*` tags;
- rewrites internal `<a href>` nav (and bare `#…` anchors) to stay inside the prefix,
  because `<base href="/">` would otherwise send them to the English root.

Rendering is a pure string transform (no DOM library) and is memoized per
`(prefix, page)`; `DEBUG_MODE` bypasses the cache for local dev. Caches are
process-lifetime, so a content change is picked up on the next deploy/restart.

### Client — the URL is authoritative

Three ES-module scripts in `public/scripts/`, on every page:

| Script | Role |
|---|---|
| `language-detect.js` | Picks the language: **on a localized URL the URL wins**; otherwise `localStorage.selectedLanguage`, else `navigator.languages`. Persists the choice and sets `<html lang>`. |
| `language-loader.js` | Fetches `languages/<lang>.json`, applies it to the DOM, keeps `<title>`/JSON-LD in sync, re-applies to dynamically-added nodes (`MutationObserver`), and re-localizes links after each apply. Exposes `window.LanguageSystem`. |
| `language-switcher.js` | The custom flag-dropdown UI over the hidden native `#language-select`. |
| `i18n-routing.js` | Shared helper: computes the localized URL for the switcher and in-app redirects, and re-localizes links after a translation pass. Takes its tables from `locale-data.js`. |
| `locale-data.js` | **Generated** — the browser's copy of the language set (prefix maps, BCP-47 codes, flags, browser-tag detection, localized paths). Do not edit; run `node scripts/build-i18n-seo.js`. The frontend cannot import `lib/i18n/locales.js` (only `public/` is served), so this file is how the source of truth crosses the boundary. |

Key behaviors that differ from a pure client-side system:

- **Switching language navigates** to the localized URL (a full load the server renders
  in-language) instead of swapping strings in place — so the URL, canonical, and
  hreflang always match what the visitor sees.
- **`localizeLinks()`** re-prefixes internal links after every translation apply, because
  applying `[data-lang-html]` resets links inside translated rich text to their raw JSON
  form (bare `#…` anchors, `terms.html`, …) which would break under `<base href="/">`.
- The **English root still client-swaps** to the visitor's stored language (invisible to
  crawlers, which have no `localStorage`), preserving the previous auto-language UX.

If a language file fails to load, the loader falls back to a tiny built-in English object
so the page never renders empty.

## Marking text for translation

Add a `data-*` attribute whose value is a **dot-path key** into the language JSON. The
server (SSR) and client apply these identically:

| Attribute | Effect | Example |
|---|---|---|
| `data-lang="key"` | Sets `textContent` (or `placeholder` on text `<input>` / `<textarea>` — client-side only). | `<h1 data-lang="hero.title.free">Free</h1>` |
| `data-lang-html="key"` | Sets `innerHTML` — use when the string contains markup. | `<p data-lang-html="home.masking.subtitle">…</p>` |
| `data-lang-attr="key\|attr"` | Sets an arbitrary attribute. | `<img data-lang-attr="navigation.logoAlt\|alt">` |

**Nodes added after load** are caught by a `MutationObserver` on `document.body`: when an
added node carries (or contains) one of these attributes, the whole pass re-runs. Note
that applying `[data-lang-html]` writes `innerHTML`, which is itself a mutation of the
watched subtree — so the observer **drains its own records** (`takeRecords()`) after each
pass. Without that, a translated value containing a `data-lang` would make the pass
re-trigger on its own output, forever, hanging the tab. No pack nests one today, but that
is not an invariant a translator can be asked to hold, so the drain is what makes it safe
rather than lucky. Guarded by
[`test/frontend/language-loader-observer.test.js`](../../test/frontend/language-loader-observer.test.js).

Also handled automatically: `<title data-lang="meta.title">`, and the page's
`application/ld+json` `name`/`description`/`keywords` (refreshed from the page's title /
description / `meta.keywords` keys). Always keep the **English** text inline as the
default (it's the root-URL content and the pre-JS fallback).

> **Form fields are client-only.** `<input>`/`<textarea>` with `data-lang` set a runtime
> *placeholder*, not content — the SSR renderer skips them so it never pre-fills the
> field with placeholder text; the client localizes them on load.

> **`data-lang` replaces the element's whole content.** It assigns `textContent` (client)
> / rewrites the element's inner HTML (SSR), so **any markup nested inside a `data-lang`
> element is destroyed** on the first translation pass. To translate a label that sits
> next to other markup — an icon, a badge — give each piece its own sibling span and
> leave the wrapper without a `data-lang`. The room-type dropdown's "New" badge is the
> worked example; see [`frontend.md`](frontend.md#the-custom-select).

### Translated label vs. submitted value

A localized label is for humans; it must not become the value the API receives. The
room-type dropdown keeps the two apart: `data-value="Dorm"` is the untranslated wire value
(and the key `promptMatrix` is looked up by), while `data-lang="roomTypes.dorm"` only
changes what the user reads. A translated value reaching `/api/process-image` would miss
the matrix and stage from the generic prompt.
[`e2e/stage-room-type.spec.js`](../../e2e/stage-room-type.spec.js) pins this by submitting
from a localized page and asserting the English value on the wire.

## The language files

- Location: `public/languages/<language>.json` (e.g. `english.json`, `french.json`).
- **`english.json` is the source of truth** for the key set. Every other file mirrors its
  structure; keys are the dot-paths referenced by `data-lang*` attributes.
- A test enforces that **every language file is valid, non-empty JSON and covers the keys
  in `english.json`** (see [`testing.md`](testing.md)) — a missing key fails CI.

## The build step — run after changing locales/pages

Three artefacts are generated from `lib/i18n/locales.js`:

- `sitemap.xml` — per-language `<url>` entries + `xhtml:link` alternates;
- the **hreflang cluster** baked into each static English page;
- `public/scripts/locale-data.js` — the browser's copy of the language set.

```bash
node scripts/build-i18n-seo.js
```

**Rerun it after** changing the language set, the page set, or a page's canonical. It's
idempotent and preserves each file's line endings. Drift-guard tests
([`i18n.test.js`](../../test/i18n/i18n.test.js) for the sitemap/hreflang,
[`locale-data.test.js`](../../test/i18n/locale-data.test.js) for the frontend tables and
the switcher markup) fail if any committed artefact is stale — so a forgotten rebuild
blocks the deploy.

## Adding or changing a string

1. Add the key + English value to `english.json`.
2. Add the **same key** to every other `languages/*.json` (the coverage test fails on a
   gap).
3. Reference it from the HTML with `data-lang` / `data-lang-html` / `data-lang-attr`,
   keeping the English text inline as the default.

No rebuild is needed for a string change — only the JSON and HTML.

### Strings that come from the server, not the HTML

Most keys are resolved from markup via `data-lang`. A few are looked up **in JS** against a
value the server returned. `errors.unstageable.*` is the one to know about; the same
code-not-prose pattern is used for the enterprise `PUBLIC_EMAIL_DOMAIN` refusal
(`enterprise.errors.publicDomain`, see the table below), so the domain list stays
server-side with nothing to keep in sync in the browser.

The upload gatekeeper (`/api/validate-image`) rejects a photo with a stable category
**code** — `PERSON_PORTRAIT`, `ANIMAL`, `FOOD`, `DOCUMENT`, `VEHICLE`, `UNRELATED_OBJECT`,
or the generic `UNSTAGEABLE` — plus the canonical English copy. The browser
([`public/scripts/unstageable-message.js`](../../public/scripts/unstageable-message.js))
renders `errors.unstageable.<CODE>` from the pack and uses the server's English only as the
fallback. So **adding a rejection category to
[`lib/staging/unstageable.js`](../../lib/staging/unstageable.js) is also a translation
job**: add the key to all 11 packs.

Because the fallback is English rather than a visible break, a missing key would ship
silently — [`test/i18n/unstageable-i18n.test.js`](../../test/i18n/unstageable-i18n.test.js) is the
drift guard that fails the build instead (missing key, stale key, or a non-English pack
still holding the English string).

### Key blocks tied to backend data

Two blocks must stay in step with server-side lists, and both have a drift guard because
neither fails loudly on its own:

| Block | Backed by | Guard |
|---|---|---|
| `errors.unstageable.*` | the rejection taxonomy in [`lib/staging/unstageable.js`](../../lib/staging/unstageable.js) | [`test/i18n/unstageable-i18n.test.js`](../../test/i18n/unstageable-i18n.test.js) |
| `enterprise.errors.publicDomain` | the public-mailbox-provider gate in [`lib/data/public-email-domains.js`](../../lib/data/public-email-domains.js) — the `PUBLIC_EMAIL_DOMAIN` refusal from `/api/enterprise/create-checkout` | [`test/data/public-email-domains.test.js`](../../test/data/public-email-domains.test.js) |
| `roomTypes.*` | [`lib/staging/promptMatrix.js`](../../lib/staging/promptMatrix.js), the `#room-type-select` options, and the AI Designer routing enum | [`test/i18n/room-types-i18n.test.js`](../../test/i18n/room-types-i18n.test.js) |

Adding a room type is therefore also a translation job — the full checklist is in
[`architecture.md`](architecture.md#adding-a-room-type).

## Adding a new language

The language is referenced by its lowercase name (e.g. `portuguese`) and a short URL
prefix (e.g. `pt`). Keep these in sync:

1. **`public/languages/<language>.json`** — a full translation of `english.json`.
2. **The flag asset** under `public/media-webp/flags/`.
3. **`lib/i18n/locales.js`** — add a `LOCALES` entry (`prefix`, `lang`, `hreflang`,
   `bcp47`, `ogLocale`, `label`, `flag`). This drives the routes, sitemap, hreflang,
   **and every frontend table**.
4. **Run `node scripts/build-i18n-seo.js`** — regenerates the sitemap, each page's
   hreflang cluster, and `public/scripts/locale-data.js` (the browser's copy of the
   language set: prefix maps, BCP-47 codes, flags, browser-tag detection).
5. **The switcher markup** in each page that has one — the `<option>` in
   `#language-select` and the `<li class="lang-switch__option">` in the custom list.
6. **The prefix regex in the two studio gates** —
   [`ai-designer-gate.js`](../../public/scripts/ai-designer-gate.js) and
   [`masking-studio-gate.js`](../../public/scripts/masking-studio-gate.js) each inline
   `/^\/(es|fr|…)(\/|$)/`. See [below](#why-the-gates-hardcode-the-prefix-list) for why
   they cannot import it.

> Steps 5 and 6 are the parts the build cannot do for you; the markup is repeated across
> eight pages, so grep for an existing language name (e.g. `italian`) to find every spot.
>
> Steps 3–6 are **test-enforced**: [`test/i18n/locale-data.test.js`](../../test/i18n/locale-data.test.js)
> fails the build if `locale-data.js` is stale, if any frontend script goes back to
> hard-coding the language list, if a page's switcher markup does not match the locale
> set exactly, or if either gate's inlined prefix list falls behind. Adding a language
> halfway can no longer ship green — which it could until 2026-07-27, when the frontend
> kept five hand-maintained copies of this list and no test compared any of them to
> `locales.js`.

### Why the gates hardcode the prefix list

`ai-designer-gate.js` and `masking-studio-gate.js` are **render-blocking classic
scripts** — `<script src>` in `<head>` with no `defer`, so they run before the body
paints. That is the whole point: they hide or redirect a Stagify+-only page *before*
it is visible. An ES module is deferred by definition, so importing `locale-data.js`
would move the gate after the paint it exists to prevent. Each therefore inlines the
prefix regex and its own copy of `localeTarget()`.

The duplication stays; what it needed was a guard, because the failure is silent. With
an eleventh locale added and the regexes left short, a signed-out visitor on
`/pl/ai-designer.html` is bounced to the **English** homepage rather than `/pl`, and a
signed-in one whose plan check stalls is thrown out of their language six seconds
later — no error, no failed request, just the wrong language. The spec above pulls
`localeTarget()` out of each gate's source and runs it against every prefix
`locales.js` serves, so the day a locale is added, both gates fail until they are
updated. It also pins that only these two files carry such a list, and that their two
copies have not drifted apart from each other.

## Adding a page to the localized set

Add it to `LOCALIZED_PAGES` in [`lib/i18n/locales.js`](../../lib/i18n/locales.js)
(`path`, `file`, `lastmod`, `changefreq`, `priority`) and run
`node scripts/build-i18n-seo.js`. The route, sitemap entries, and hreflang follow
automatically.

## BCP-47 mapping

`<html lang>` uses BCP-47 codes, defined once in `lib/i18n/locales.js` and reaching the
browser via the generated `LANG_BCP47` in `public/scripts/locale-data.js`:

```
english→en  spanish→es  chinese→zh-Hans  korean→ko  french→fr  german→de
dutch→nl  italian→it  portuguese→pt-BR  russian→ru  japanese→ja
```
