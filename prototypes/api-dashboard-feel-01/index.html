API dashboard — 9 design directions

Request: “The stagify api dashboad at api-keys.html feels really lackluster. It doesn’t feel like an actual dashboard. Use the prototype skill to improve this.”

18 Aug 2026 Target: public/api-keys.html + public/styles/developers.css Palette + gradient lifted from styles.css :root

Today it is four stacked cards — balance, keys, packs, ledger — in a 980px column, each one a flat white box of the same weight, so nothing is the headline and there is no sense of an instrument reading out a live system. Every number below is either already returned by /api/api-credits and /api/api-keys, or already sitting in the api_requests table (key_id, status, credits_charged, attempts, claimed_at) with no read endpoint yet — the variants that show usage charts assume one new GET /api/api-usage and say so in their badges.

1Console Rail

Pick this when the goal is “stop feeling like a settings page and start feeling like a product you log into.” A persistent left rail turns four sections into five destinations, so the page can grow — logs, webhooks, team — without ever getting taller. The KPI strip is doing the real work: it answers “is my integration healthy right now?” before you have scrolled, which is the question today’s page never even asks. The cost is that it is the most conventional answer here; nobody will be excited, everybody will know how to use it.

+ Room to grow without new pages + Health answered above the fold + Familiar to anyone who uses Stripe/Vercel − Rail is dead weight at 5 sections − Reads as generic SaaS, not as Stagify
Media none JS tab switcher, ~40 lines over today’s islands Mobile rail collapses to a scrolling tab strip API needs GET /api/api-usage for the KPI strip A11y tablist/tabpanel, straightforward vs today 4 stacked cards → 1 screen, 0 scroll to keys

2Bento Deck

Pick this when you want the page to feel like an instrument the moment it paints, with no navigation to learn. Everything lives on one screen at different weights: the balance is enormous and gradient-filled so it reads as the headline, usage is a glanceable bar field, keys shrink to two lines, and packs become a buy strip rather than a section. It is the direction that makes the strongest first impression in a screenshot — and the one that will fight you hardest the day you add a sixth thing to show.

+ Feels designed, not assembled + Zero navigation to learn + Buying is one click from anywhere − Grid breaks down as content grows − Long ledgers have nowhere to live
Media none — the gradient does the lifting JS lightest of the nine; today’s islands re-slotted Mobile 4-col → 2-col → stacked; hero first API usage tile needs GET /api/api-usage vs today ~2,100px page → ~640px, no scroll on a laptop

3Key-First

Pick this if you believe the page has exactly one job — managing keys — and the other three cards are supporting cast that got equal billing by accident. The balance shrinks to a ribbon that is always on screen, and each key becomes an expandable unit that carries its own stats, its own ready-to-paste curl with its own prefix, and its own danger zone. It is the least “dashboard-looking” option here, and it is also the one that makes the most sense the fifth time you visit rather than the first.

+ Every action is where the object is + Scales to 25 keys without redesign + Smallest diff from today’s markup − Weak first impression; still list-shaped − Account-wide health is only a ribbon
Media none JS accordion + copy-to-clipboard; keeps key-list.js Mobile best of the nine — rows collapse naturally API per-key usage from api_requests.key_id A11y aria-expanded rows; no new focus traps vs today revoke/rotate/test 3 clicks → 1 row

4Quickstart Cockpit

Pick this if the real problem is not that the page is boring but that it is inert — you get a key and then you are on your own, one tab away in the docs. Here the left half is a live quickstart whose curl is bound to the key you pick from a dropdown, and the right half is your request log streaming in, so the first call you ever make appears on the same screen you copied it from. It is the direction that most improves day one and does the least for day ninety, when you already know the API and just want your balance.

+ Closes the gap between key and first call + Live log proves the integration works + Strong dev-rel story; screenshots well − Wasted space for a returning user − Streaming log needs polling or SSE
Media none JS heaviest — poller + snippet binding + clipboard Mobile stacks; log falls below the fold API needs GET /api/api-requests (paged) or SSE I18n code snippets stay English by design vs today key → first successful call: 2 tabs → 1

5Usage-First (keys in a drawer)

Pick this if you accept that keys are a once-a-quarter task and usage is a daily one, and you are willing to demote the thing the page is named after. The chart is the page; keys and billing slide in from the right when you actually need them, which keeps the main surface uncluttered and makes the dashboard worth opening on a Monday morning. The risk is real: someone arriving from the docs looking for “where do I get a key” has to find a button first.

+ Genuinely worth revisiting daily + Failure spikes are visible, not buried in a ledger + Drawer keeps rare tasks out of the way − Buries the page’s namesake behind a button − Empty and sad for a brand-new account
Media none — chart is CSS bars, no library JS drawer + range toggle + chart build Mobile drawer goes full-screen; chart scrolls API GET /api/api-usage?range= is a hard dependency A11y drawer needs a real focus trap + Esc vs today 0 → 30 days of history visible at a glance

6Inspector (master / detail)

Pick this when you expect accounts with a dozen keys — agencies with a key per brokerage — and today’s single flat list would become unreadable. The left column is the account’s whole object graph, including billing as just another selectable thing, and the right is a proper record view with fields, history and a danger zone that is visually walled off. It is the most durable structure here and the coldest: it reads like an admin console, which is fine for an API dashboard and wrong for a marketing surface.

+ Handles 25 keys as gracefully as 2 + Destructive actions properly quarantined + Deep-linkable per key (#key/stg_live_9f3a) − Two clicks to any number; nothing at a glance − Master/detail is awkward on a phone
Media none JS selection + hash routing; ~70 lines Mobile weakest — needs a list→detail push view API per-key stats; rename already exists (PATCH) A11y listbox semantics; keyboard nav needed vs today scales to 25 keys; today’s list wraps past ~6

7Console Mode THE SWING

Pick this if you want the API surface to have a personality the rest of the site cannot have, and you are prepared to defend it. It treats the dashboard as a REPL: keys ls, credits, usage --7d, keys new "Production" — typed or clicked — printing monospace tables that look exactly like what a developer sees in their own terminal. It is genuinely faster once learned and genuinely hostile to anyone who is not a CLI person, which is why it should ship as a mode behind a toggle rather than as the page. Try the buttons; it really runs.

+ Nothing else on the web looks like this + Keyboard-first; fastest for repeat users + Commands map 1:1 to a future stagify CLI − Hostile to non-CLI users; must be a toggle − Screen-reader and i18n story is genuinely poor
Media none · mono webfont already loaded elsewhere JS command parser + output renderer, ~200 lines Mobile poor — an on-screen keyboard fights it I18n commands stay English; 11 packs untouched A11y needs a live region + a full non-terminal fallback vs today revoke a key: 4 interactions → 1 typed line

8Runway

Pick this if the failure that actually costs money is running out of credits mid-batch at 2am, and everything else on the page is secondary to preventing it. The dial answers one question — how long until I stop rendering — and the auto-top-up rule turns that from a thing you monitor into a thing you configure once. It is the only variant that adds a feature rather than rearranging pixels, which is both why it is the most valuable and why it is the most expensive: saved cards, a rule engine and a charge-without-checkout path that Stripe Checkout does not currently give us.

+ Prevents the one failure that loses revenue + Auto-top-up is a retention feature, not decoration + One number anyone can read in a second − Needs saved payment methods + a rule engine − Keys become an afterthought on their own page
Media none — SVG dial, no library JS dial arc + rule form; modest Mobile good — dial then stacked cards Backend largest lift: SetupIntent, off-session charge, cron Email reuses the admin email catalog for low-balance alerts vs today “am I about to run out?” unanswerable → 1 glance

9Adaptive

Pick this if you think the page feels lackluster mostly because it is the same page for someone with no key, someone shipping 800 renders a week and someone who is suspended — three completely different situations wearing one layout. Here the dashboard changes shape: day zero is a quickstart with the metrics hidden because they would all read zero, active is a real instrument, and trouble takes over the whole surface until it is resolved. The catch is that you are building and maintaining three pages, and testing them means fixtures for each.

+ No empty dashboard on day one + Suspension is impossible to miss + Composes with any other variant here − Three states to build, test and translate − A layout that shifts under you can disorient
Media none JS state selection from the data already fetched Mobile same as whichever base variant it wraps API nothing new — suspended + keyCount + balance suffice Test 3 e2e fixtures instead of 1 vs today new account sees 4 empty cards → 1 clear next step

Notes for whoever builds this

  • What already exists: /api/api-credits returns balance, lifetimePurchased, lifetimeSpent, suspended, keyCount and 50 ledger rows; /api/api-keys returns name, prefix, createdAt, lastUsedAt, revokedAt. Variants 3 and 9 need nothing else.
  • What needs one new endpoint: every chart and per-key stat above reads api_requests, which already stores key_id, status, credits_charged, attempts, claimed_at and completed_at. A single GET /api/api-usage?range= covers variants 1, 2, 4, 5 and 6.
  • What needs real backend work: only variant 8 — saved cards (SetupIntent), off-session charging, and a rule the webhook path can trigger. Everything else is presentation.
  • Styling: the palette, the CTA gradient and the button shapes come from styles.css :root and developers.css. A new sheet is not needed; developers.css is shared with developers.html, so anything added there should stay under a .dev-app scope.
  • Not addressed here: localisation. api-keys.html is noindex and English-only today; none of these variants assume otherwise.
