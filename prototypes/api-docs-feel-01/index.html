Sidebar Reference

The safe, boring, correct answer — and the one a developer's eye actually recognises as documentation. Persistent left nav, breadcrumb, an opaque white canvas that kills the gradient, and a right-hand “On this page” rail. Pick this if the goal is credibility rather than distinctiveness: it looks like every docs site your customers already trust, which is the entire point. Stagify API

Stage a real-estate photo from your own code. One HTTP call returns one staged image. Prepaid credits at $0.15 an image — no subscription, no minimum, no invoice at the end of the month.

Base URL  https://stagify.ai/api/v1  ·  all requests need Authorization: Bearer stg_live_…

Your first render

Create a key on your API keys page, buy a credit pack, then post a photo. The response carries the staged image as a data URL.

# one image, one credit
curl https://stagify.ai/api/v1/renders \
  -H "Authorization: Bearer $STAGIFY_API_KEY" \
  -H "Idempotency-Key: $(uuidgen)" \
  -F "image=@living-room.jpg" \
  -F "roomType=Living room" \
  -F "furnitureStyle=modern"

Rate limits

60 renders per 5 minutes per key, and 3 simultaneous renders per key. Over either ceiling you get 429 or 409 CONCURRENCY_LIMIT.

02

Split-Pane (prose left, sticky code right)

The Stripe/Twilio shape: explanation scrolls on the left, a dark code panel sits fixed on the right and swaps its sample as you move between sections. This is the layout that most reads as “serious API company”, and it solves a real problem — the reader never loses the request while reading about a parameter. Choose it if you want the page to feel expensive. The cost is that it demands two columns of genuinely parallel content: any section without a natural code sample leaves a hole in the right rail, and you only have four endpoints to fill it with.

+ Highest “real API docs” signal + Code always visible while reading prose + Language tabs have an obvious home − Needs paired content for every section − Collapses to a plain stack under ~1000px
MEDIA none JS ~60 lines: IntersectionObserver + tab state MOBILE degrades to variant 1; code inlines after each section A11Y scroll-linked panel needs aria-live care vs today same content, ~40% less vertical scroll on desktop

Create a render

Stages one photo and returns it. The credit is taken before the model runs and refunded automatically if the render fails, so you only ever pay for an image you received.

image
file · required
JPEG, PNG or WebP. Up to 25 MB.
roomType
enum
One of 8 values. Case-sensitive, and an unknown value is passed to the model verbatim rather than rejected.
furnitureStyle
enum
Defaults to standard, which is also what an unrecognised value becomes.
Request
curl -X POST https://stagify.ai/api/v1/renders \
  -H "Authorization: Bearer $KEY" \
  -F "image=@room.jpg" \
  -F "roomType=Living room"
Response
{
  "id": "req_8Kd2mQ",
  "object": "render",
  "status": "succeeded",
  "image": "data:image/webp;…",
  "credits": { "charged": 1 }
}

03

Spec Sheet (austere, no cards at all)

Delete every box. One column, hairline rules, tight leading, field names in a monospace left gutter — closer to an RFC or a man page than to a website. This is the cheapest direction by far: it is almost entirely subtraction from what you already have, and it fixes the “marketing” feel by removing the exact thing causing it. Pick it if you want the page to feel authoritative without committing to navigation you do not yet need. The risk is that austerity reads as unfinished to a non-technical buyer who lands here from the footer.

+ Cheapest to build — mostly deletion + Extremely fast to scan + No new components or JS + Prints and copy-pastes cleanly − Can read as austere or unpolished − No wayfinding once it grows
MEDIA none JS none MOBILE best of all eight — it is already one column A11Y strongest: pure semantic flow, no widgets vs today ~35% shorter page; ~0 new CSS beyond removals

API Reference · v1

Stagify API

One HTTP call, one staged photo. $0.15 an image, prepaid.

POST  /api/v1/renders

Stage one photo. Charges one credit, refunded on failure.

Parameters
image
file, required. JPEG, PNG, WebP. ≤ 25 MB. Checked on MIME type, not extension.
roomType
enum, default Living room. Bedroom · Living room · Dining room · Kitchen · Office · Bathroom · Outdoors · Dorm. Case-sensitive; an unknown value is not rejected — it is written into the prompt as free text.
furnitureStyle
enum, default standard. standard · modern · midcentury · scandinavian · luxury · coastal · farmhouse · custom.
stampScale
number, 0.7–1.6, default 1. Out-of-range values are clamped, not refused.
curl https://stagify.ai/api/v1/renders \
  -H "Authorization: Bearer $KEY" -F "image=@room.jpg"

Try-It Console (docs as a playground)

Put a working request builder at the top: pick the enums from real dropdowns, watch the cURL assemble itself, hit Send. This is the only direction that turns your soft-failing enums from a documentation problem into a non-problem — a developer who picks Living room from a select can never typo it into Living Room and silently get the fallback prompt. Pick it if adoption matters more than elegance. It is also the most expensive and the only one that needs a spend-free sandbox, or it will burn real credits on curiosity.

+ Eliminates the case-sensitivity trap entirely + Shortest possible time-to-first-call + Doubles as living proof the API works − Needs a sandbox key or it costs real money − By far the most code to build and keep working
MEDIA a sample room photo, plus a rendered result JS ~200 lines + a real fetch; the heaviest option MOBILE form stacks; the console is desktop-first in practice A11Y a real form — labels and errors must be done properly SECURITY must never accept a live key in the browser vs today first successful call in ~30s instead of “copy, edit, guess”

Task Recipes (organised by job, not by object)

    
Stop describing the API and start describing the jobs: “Stage your first photo”, “Handle a failed render”, “Never get double-charged”, “Go to production”. Each is a numbered walkthrough with the reference folded in where it is needed. Pick this if your buyer is a small real-estate-software team rather than a platform engineer — they do not want a parameter catalogue, they want the four things they will actually do. The tradeoff is real: task docs are worse than reference docs for the reader who already knows what they want and just needs the enum list, so this direction really wants variant 1 or 3 living next to it.

06
Code Spine — the unconventional swing

    
Invert the hierarchy. One annotated request runs down the centre of a dark page as the spine of the whole document, and the prose lives in the margin as numbered annotations hanging off individual lines. Literate programming, applied to an HTTP call. Nobody else's API docs look like this, which is precisely the argument for and against it: it is genuinely memorable and it makes the “one call, one image” story visceral, but it only works because your API is one endpoint, and it will fight you the moment there is a fifth. Propose it knowing it is a swing.

    

      + Nothing else on the web looks like it
      + Perfectly suits a single-call API
      + Dark surface is maximally “not marketing”
      − Breaks down past a handful of endpoints
      − Margin annotations are hard on mobile and on screen readers
    

    

      MEDIA none
      JS ~80 lines: line↔annotation linking and hover sync
      MOBILE the weakest — annotations must reflow inline, losing the concept
      A11Y hardest: annotation order must make sense linearised
      THEME dark-only; needs its own palette outside the site tokens
      vs today one screen instead of six; highest risk

POST /api/v1/renders

        

          
curl https://stagify.ai/api/v1/renders \
  -H "Authorization: Bearer $KEY" ①
  -H "Idempotency-Key: $(uuidgen)" ②
  -F "image=@living-room.jpg" ③
  -F "roomType=Living room" ④
  -F "labelVirtuallyStaged=true" ⑤

          

            
① The key
Header only, never a query string. A stolen key costs at most your remaining balance.

            
② Idempotency
Retry with the same key. This is what guarantees you are never charged twice.

            
③ The photo
JPEG, PNG or WebP, up to 25 MB. MIME type is what's checked.

            
④ Case matters
Eight values. Living Room is not Living room — the wrong one isn't rejected, it's pasted into the prompt.

            
⑤ Disclosure
Burns the MLS/NAR label into the pixels. If it can't be applied the image is withheld and refunded.

07
Endpoint Explorer (OpenAPI-shaped)

    
Every endpoint is a collapsed row — method badge, path, one-line summary — and expands in place to parameters, responses and a sample. It looks auto-generated, which is a compliment in this context: it signals a spec exists behind the page. Pick it if you plan to publish an OpenAPI document, because then this page becomes a rendering of the spec rather than prose that can drift from it. The honest downside is that generated-looking docs are also generated-feeling — there is nowhere natural to explain why credits are refunded or why the disclosure cannot be switched off.

    

      + Whole API visible in one screen
      + Natural home for a real OpenAPI spec
      + Adding an endpoint is adding a row
      − No room for the reasoning that makes your API trustworthy
      − Reads as impersonal / boilerplate

      JS ~50 lines of disclosure; or generate from a spec at build time
      MOBILE good — rows collapse naturally
      MAINT best long-term if the spec becomes the source of truth

08
Ladder + Reference Drawer

    
Keep one loud job above the fold — a three-rung ladder from “no account” to “first staged image”, with copy buttons and a visible progress state — and push the entire reference into a slide-over drawer opened from a persistent “API reference” button. It is the only direction that treats the two audiences separately instead of averaging them: the evaluator gets a landing page that converts, the integrator gets a reference that never makes them scroll past marketing. The cost is that reference material in a drawer is not linkable or indexable unless you do extra work, which matters for a page you want ranking on “virtual staging API”.

    

      + Serves evaluator and integrator without compromise
      + Reference is one click from anywhere on the page
      + Keeps the site's visual identity intact
      − Drawer content is weak for SEO and deep links
      − Two shells to maintain instead of one
    

    

      MEDIA optional before/after in rung 3
      JS ~70 lines: drawer, focus trap, copy buttons
      MOBILE drawer goes full-screen; ladder stacks well
      SEO weakest — reference must still render in the DOM to be indexed
      A11Y drawer needs a proper focus trap and Escape
      vs today above-the-fold does one job instead of four
